# docs/security/

Security gates for this repository, generated by
`sunaba new --stack security-ci`.

| Check (job name) | Tool | What it catches | Blocks? |
|---|---|---|---|
| `SAST (Semgrep)` | Semgrep, `p/security-audit` + `p/owasp-top-ten` | Injection, SSRF, XSS, unsafe deserialisation, weak crypto, and similar patterns in code | Yes, from day one |
| `Dependency Scan (Trivy)` | Trivy `fs --scanners vuln` | HIGH/CRITICAL vulnerabilities with a fix available, in production dependencies of any lockfile (npm, pnpm, yarn, bun, uv, poetry, pip, Go, Cargo, …) | Stage 0: warns (the job stays green; the job summary shows the counts). Stage 1: blocks. Always fails if Trivy itself fails |
| `Secret Scan (Gitleaks)` | gitleaks (`--stack secrets`) | Committed credentials | Yes |

A red check does **not** block the merge button until the check is
*required*. Run `scripts/protect-branch.sh` (below) to make it so.

## Maturity ladder

Promote the gates as the project matures, never by weakening them.

| Stage | When | Do |
|---|---|---|
| **0 — Day one** (default) | New project | Semgrep and gitleaks block; Trivy warns |
| **1 — Dependencies triaged** | Trivy warnings reviewed; accepted ones in `.trivyignore` with a reason and an expiry | `gh variable set SUNABA_TRIVY_BLOCKING --body true` (a repository variable, so `sunaba rebuild` cannot reset it) |
| **2 — Enforced** | The checks have passed on the default branch; you are a repository admin | `scripts/protect-branch.sh` (add `--branch staging` for an integration branch) |
| **3 — Tightened** | Few false positives, a stable team cadence | Add rulesets (e.g. `--config p/cwe-top-25`), lower Trivy's `--severity` to include MEDIUM, run `protect-branch.sh --strict` |

## When a gate fails

**Semgrep finding:**

1. Fix the code. The finding links to the rule and usually shows a
   safe pattern.
2. For a false positive, suppress **that line only**, with a reason:
   `# nosemgrep: <rule-id> — input is a constant from settings.py`.
3. Do not exclude source directories. Semgrep already skips
   `node_modules/`, `dist/`, `build/`, `vendor/`, `.venv/` and test
   directories. Creating a `.semgrepignore` **replaces** that default
   list, so restate the defaults if you ever add one.

**Trivy finding:** upgrade the package (Dependabot often has the PR
open already). Vulnerabilities with no fixed version are not reported
(`--ignore-unfixed`): the gate asks only for what you can act on. To
see them anyway, run `trivy fs --scanners vuln .` locally. If you must accept a finding, add its ID to
`.trivyignore` with a reason and an expiry:

```
# lodash prototype pollution — not reachable: we never merge user input. Revisit 2026-12-31.
CVE-2021-23337 exp:2026-12-31
```

What Trivy does not cover:

- Dev dependencies are skipped. To include npm/yarn dev dependencies,
  add `--include-dev-deps`.
- The binary `bun.lockb` is not read; commit the text `bun.lock`.
- It trusts the lockfile. A lockfile that is out of date gives stale
  results.
- Its advisory data and severities can differ from `npm audit`'s.

**"did not complete" / exit 2+ errors:** the scanner itself failed
(network, registry outage, parse error). The job fails closed on
purpose; re-run it, and fix the cause rather than the workflow.

`.semgrepignore` and `.trivyignore` are yours: sunaba never generates
or overwrites them.

**Protect the gates themselves.** A required check matches a job
*name*. A pull request that edits the workflow, for example by removing
`--error` while keeping the job name, still produces a green check. So
treat these files as security-sensitive and require a reviewer for
them:

- `.github/workflows/`
- `scripts/protect-branch.sh`
- `.semgrepignore` and `.trivyignore`
- `nosemgrep` comments
- `CODEOWNERS` itself

A `CODEOWNERS` entry plus "Require review from Code Owners" in the
ruleset does this. sunaba does not generate one, because only you know
who the owners are.

## Making the checks required

```sh
scripts/protect-branch.sh --dry-run            # print the ruleset JSON
scripts/protect-branch.sh                      # default branch
scripts/protect-branch.sh --branch staging     # plus an integration branch
```

Before it changes anything, the script checks that every required
check has **already passed on the default branch's latest commit** and
was reported by GitHub Actions. If any has not, it stops and says which
one. Requiring a check that has never passed would block every PR.
Commit and push the workflows first, and fix what they find.

Each check is then bound to the GitHub Actions app, so no other app
can satisfy it by reporting a status with the same name. `--force`
skips the preflight and the binding (not recommended).

The script creates (or updates) one repository ruleset,
`sunaba security gates`:

- it requires every check that the workflows in `.github/workflows/`
  define;
- it blocks force pushes and branch deletion;
- it allows no bypass, admins included.

It needs `gh`, authenticated as a repository admin.

Rulesets are available on public repositories and on private
repositories with GitHub Pro, Team, or Enterprise — **not on free
private repositories**. There, the checks still run and report on
every PR; only the merge button stays unlocked.

Things to know:

- **First run.** GitHub knows a check only after it has run once.
  Push or open a PR after adding the workflow, or PRs wait on the
  never-reported checks.
- **Fork PRs.** A first-time contributor's workflow runs need
  approval. Until you approve them, the required checks stay pending.
- **Merge queue.** The workflow also runs on `merge_group`, so the
  checks work with GitHub's merge queue.
- **Unique names.** Required checks match on job name. Don't reuse
  `SAST (Semgrep)`, `Dependency Scan (Trivy)` or
  `Secret Scan (Gitleaks)` in another workflow.
- **Undo.** Go to Settings → Rules → Rulesets → `sunaba security gates`,
  then disable or delete it. Re-running the script updates that
  ruleset; if several rulesets share the name, the script refuses to
  guess.

## Running the gates locally

```sh
docker run --rm -v "$PWD:/src" -w /src semgrep/semgrep:1.178.0 \
  semgrep scan --error --metrics=off --config p/security-audit --config p/owasp-top-ten .
trivy fs --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed .
```

Trivy downloads its vulnerability database on every run (from
`mirror.gcr.io` by default). A registry rate limit or outage fails the
job closed; re-run it. A `GITHUB_TOKEN` does not help with those
limits. Caching the database with `actions/cache` saves time, but it
adds an action to trust.

Semgrep downloads the two rulesets from the Semgrep Registry on
every run. The engine version is pinned, but the rules are not, so a
new rule can flag old code. That is usually what you want. Don't copy the
registry rules into your repository: the Semgrep-maintained rules are
under the [Semgrep Rules License](https://semgrep.dev/legal/rules-license/),
which does not allow redistributing them. Rules you write yourself can
live in the repository and be passed with `--config path/to/rules/`.

## Updating the scanners

Dependabot updates the SHA-pinned actions, but not these values in
`.github/workflows/security-scan.yml`:

- **Semgrep:** take the new version tag's multi-arch *index* digest
  from Docker Hub, and update `image:` as
  `semgrep/semgrep:<version>@sha256:<digest>`.
- **Trivy:** set `TRIVY_VERSION`. Take `TRIVY_SHA256` for
  `trivy_<version>_Linux-64bit.tar.gz` from the release's
  `trivy_<version>_checksums.txt`, and confirm the release is marked
  *immutable*. Before trusting the new hash, verify the asset's Sigstore
  bundle, for example:

  ```sh
  uvx --from sigstore sigstore verify github \
    --bundle trivy_<version>_Linux-64bit.tar.gz.sigstore.json \
    --repository aquasecurity/trivy --ref refs/tags/v<version> \
    trivy_<version>_Linux-64bit.tar.gz
  ```
 Trivy was compromised in March 2026
  ([GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23)),
  so never switch to a mutable tag or `latest`.
