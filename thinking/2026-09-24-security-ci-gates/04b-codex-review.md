1. **Rulesets vs classic branch protection.** Use repository rulesets. They are the better generated helper target in 2026: broader branch targeting, one named object to update, and public Free support. The caveat is plan support: rulesets are available for public repos on Free, but private repos require Pro/Team/Enterprise. `~DEFAULT_BRANCH` is documented for ruleset ref conditions, and extra branches should be emitted as `refs/heads/<name>`, not ambiguous bare names. Idempotent update by name is fine, but fail loudly if multiple matching names are found. Requiring checks by `context` without `integration_id` is acceptable for a generic template; adding an expected app source is stronger, but GitHub requires the app to have recently submitted the check and be associated with an existing required check, which is awkward for first-run scaffolding. `strict_required_status_checks_policy` maps to “branch up to date”; default off is reasonable, `--strict` is a good opt-in. Sources: GitHub ruleset API/ref patterns and required-check parameters, expected source behavior, and plan availability. ([docs.github.com](https://docs.github.com/en/enterprise-cloud%40latest/rest/repos/rules?utm_source=openai)) ([docs.github.com](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets?utm_source=openai)) ([docs.github.com](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets?utm_source=openai))

2. **Trivy delivery.** Yes: after GHSA-69fq-xp46-6x23, a pinned, checksum-verified release binary is preferable to adding `trivy-action` plus its setup chain. The advisory explicitly says malicious Trivy binaries/images, forced-pushed `trivy-action` tags, and replaced `setup-trivy` tags were all involved; `trivy-action` also documents that it calls `setup-trivy` by default. A SHA-pinned safe action can be acceptable, but the direct binary path has a smaller CI supply chain. I would add optional cosign bundle verification in docs or a high-assurance mode; if shipped by default, pin/verify cosign too, or you mostly move trust to another installer. Replacing npm/pnpm audit with Trivy is not a major regression for a language-agnostic template, but document limits: Trivy excludes Node dev dependencies by default, lockfile freshness matters, `bun.lockb` is unsupported, and advisory/severity sources differ from npm audit. Consider a documented `TRIVY_INCLUDE_DEV_DEPS=true` knob rather than defaulting it on. ([github.com](https://github.com/advisories/GHSA-69fq-xp46-6x23)) ([github.com](https://github.com/aquasecurity/trivy-action/blob/master/README.md?plain=1)) ([trivy.dev](https://www.trivy.dev/docs/latest/getting-started/signature-verification/)) ([trivy.dev](https://www.trivy.dev/docs/latest/guide/coverage/language/nodejs/))

3. **Semgrep.** Digest-pinned `container:` is the right default. Semgrep’s own sample GitHub Actions config uses `container: image: semgrep/semgrep` plus `actions/checkout`, so the shape is normal; pinning the digest improves it. `pip install semgrep==X --require-hashes` is reproducible but painful across wheels/transitive deps; `uvx` is convenient but less locked unless separately pinned and cached. `p/security-audit` plus `p/owasp-top-ten` is a reasonable broad SAST default, with expected false positives. Live registry rules are acceptable for an opt-in security stack because users get rule updates, but call out that builds are not fully reproducible. Do not vendor rules by default; offer a “freeze rules locally” recipe for regulated repos. Do not skip Dependabot PRs here: Semgrep’s sample skip is mainly about token/permission issues, and this workflow uses no Semgrep token or secrets. ([semgrep.dev](https://semgrep.dev/docs/semgrep-ci/sample-ci-configs?utm_source=openai)) ([github.com](https://github.com/semgrep/semgrep/blob/develop/metrics.md?utm_source=openai)) ([github.com](https://github.com/semgrep/semgrep?utm_source=openai))

4. **Informational mode.** Green job plus explicit warning is better than `continue-on-error`. It lets `Dependency Scan (Trivy)` be required immediately while preserving a clean future switch to blocking. The exit-code mapping is sound: Trivy documents that `--exit-code` sets the code used when security issues are found, while default findings exit 0; treating `3` as “findings” and every other nonzero as scanner failure is fail-closed. Keep the comparison strictly quoted, e.g. `[ "${TRIVY_BLOCKING}" = "true" ]`, and maybe print the Trivy report path or summary before the warning. ([trivy.dev](https://trivy.dev/docs/dev/guide/configuration/others/?utm_source=openai))

5. **Required contexts.** Yes, require Trivy from day one if informational mode stays green. For first-run repositories, the script can still submit exact check context names through the API; the UI may not offer them until they have run, but rulesets support exact `context` strings. The script should print the exact contexts it is requiring, warn that the first PR/push must run the workflow once, and avoid adding contexts for missing workflows. Also avoid name collisions: GitHub warns that if a check and commit status share a name, both may need to pass. No `paths:` filters is the right call because path-skipped required workflows can sit pending and block. ([docs.github.com](https://docs.github.com/en/enterprise-cloud%40latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules?utm_source=openai)) ([docs.github.com](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks?utm_source=openai)) ([docs.github.com](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax?utm_source=openai))

6. **User-owned ignore files.** Correct: do not ship `.semgrepignore` or `.trivyignore` from an overwrite-on-rebuild stack. Put examples in docs instead. Semgrep supports `.gitignore`, `.semgrepignore`, and default ignores; Trivy’s CLI default ignore file is `.trivyignore`. These are project policy files, not generated boilerplate. ([semgrep.dev](https://semgrep.dev/blog/2026/making-semgrep-rip-how-ripgrep-inspired-us-to-shave-hours-off-some-scans/?utm_source=openai)) ([trivy.dev](https://trivy.dev/docs/dev/references/configuration/cli/trivy_image/?utm_source=openai))

If you avoid `actions/cache` to keep supply chain small, document that first runs may be slower/flakier. ([github.com](https://github.com/aquasecurity/trivy-action/blob/master/README.md?plain=1&utm_source=openai)) ([github.com](https://github.com/aquasecurity/trivy/blob/main/docs/guide/references/troubleshooting.md?utm_source=openai))
