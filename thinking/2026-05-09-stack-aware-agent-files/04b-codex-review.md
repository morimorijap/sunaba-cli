## Headline position

> **Strategy D, with a "thin A" root.**
>
> - Root `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` stay ≤60 lines —
>   stack-aware **index**, not full content.
> - Detail lives in `docs/agents/<stack>.md`.
> - For Claude, mirror the same content as
>   `.claude/skills/sunaba-<stack>/SKILL.md` (with frontmatter).
> - `skills.md` is stack-composed.
> - `SECURITY.md` is **not** stack-composed.

The key idea is "the root file is an index that points at canonical
detail, not a place where canonical detail lives." This converges with
the [agents.md](https://agents.md/) spec philosophy and HumanLayer's
discipline.

## A. Strategy

**Adopt: D + compact concatenation in the root.**

Example root `AGENTS.md`:

```md
# AGENTS.md

## Sandbox
Generated by sunaba. Follow the selected stack guidance below.

## Selected stacks
- python: use `uv`; run `uv run pytest -q`; see `docs/agents/python.md`.
- nextjs: use npm/Node 22; run frontend tests from the app root;
  see `docs/agents/nextjs.md`.
- azure: use `az`; credentials come from environment;
  see `docs/agents/azure.md`.

## General rules
- Prefer the existing project commands over inventing new ones.
- Add or update tests for changed behavior.
- Do not commit `.env` or local credentials.
```

This stays under 60 lines even with 5+ stacks. Codex / Gemini get the
same `AGENTS.md` / `GEMINI.md` signal; Claude additionally lazy-loads
detail through skills. The detailed Markdown is **always** also
written to `docs/agents/<stack>.md`, so non-Claude agents can
discover it on demand.

**Why not the others (verbatim):**

- **B (`@include`).** *"Avoid — `@include` semantics aren't
  uniform across agents. As a template generator, the post-generation
  file should make sense on its own."*
- **C (skills only).** *"Too Claude-optimized."*
- **E (subdirectory AGENTS.md).** *"Valid, but sunaba doesn't
  dictate project layout. Defer until we add an explicit
  `--layout nextjs:web` flag, then generate `web/AGENTS.md`
  appropriately."*

## B. Composer / generator design

> **Do not put Markdown bodies inside `stacks/*.json`.**
> *"The current `compose.py` is a JSON deep-merge composer with a
> single responsibility. Mixing long Markdown into stack JSON ruins
> reviewability and maintenance."*

### File layout

```
src/sunaba_cli/templates/agents/
  base/
    AGENTS.md
    CLAUDE.md
    GEMINI.md
    skills.md
  fragments/
    python/
      summary.md
      tools.md
      guidance.md
    nextjs/
      summary.md
      tools.md
      guidance.md
    azure/
      summary.md
      tools.md
      guidance.md
```

### Outputs

```
AGENTS.md                              # composed from base + summary fragments
CLAUDE.md
GEMINI.md
skills.md                              # composed from base + tools fragments
docs/agents/python.md                  # = guidance.md
docs/agents/nextjs.md
.claude/skills/sunaba-python/SKILL.md  # = guidance.md + frontmatter
.claude/skills/sunaba-nextjs/SKILL.md
```

`guidance.md` is the **single source of truth**, rendered to two
targets: `docs/agents/<stack>.md` and `.claude/skills/sunaba-<stack>/
SKILL.md`. The skill version gets YAML frontmatter prepended:

```md
---
name: sunaba-python
description: Use when working on Python projects generated with sunaba --stack python.
---

# Python Stack
...same body as docs/agents/python.md...
```

### Implementation

Add `_build_agent_files(name, stacks, no_devcontainer=False)` to
`cli.py`. Keep `sync.py`'s simple-copy path. Stack-aware mode invokes
the new builder.

### Stack ordering

**Pin to the user's `--stack` flag order.** Devcontainer composition
already follows that order; matching the agent file ordering is
intuitive. Interactive selection produces deterministic ordering
because the picker uses a sorted list.

### Idempotency

Same flags → byte-identical output. Lists deduplicated;
fragment files copied verbatim.

### `--no-devcontainer`

Generate agent files. Switch wording to host-only:

```md
## Runtime
Host-only mode: required CLIs must exist on PATH.
Do not assume devcontainer features are installed.
```

> *"For this we should eventually persist `no_devcontainer` (or
> `mode`) in the registry so `sync` can choose the right wording
> automatically."*

### `sunaba sync` (the safety-critical part)

Backwards compatibility is the top priority. Codex proposes:

- Legacy registry entries default to **static copy** (today's
  behavior).
- New stack-aware projects record `agent_files: "stack-aware"` in
  the registry.
- Opt-in migration via `sunaba sync --agent-files stack-aware <name>`.
- `sunaba sync --all` follows each project's recorded mode.
- If stacks are unknown for a project but stack-aware sync was
  requested, error out and ask for explicit `--stack`.

> *"This avoids the failure mode where existing users' agent files
> get unexpectedly rewritten by `sync`."*

## C. `skills.md`

**Yes, stack-compose it.**

> *"The current union catalog suggests workflows the agent can't
> actually run — that's literally the bug we're fixing here."*

Split into base tools and stack tools:

- **Base.** Today's devcontainer base ships Node 22 and GitHub CLI;
  those go in the base catalog.
- **Stack contributions.**
  - `python` → `uv`, `pytest`
  - `nextjs` → `npm`, `vercel`
  - `aws` → `aws` CLI
  - `azure` → `az`
  - `gcp` → `gcloud`
  - `neon` → `neonctl`, `psql`
- **`agents` stack.** *"Limit its skills entry to API-key
  injection / persisted auth-state notes — `claude` / `codex` /
  `gemini` CLIs are present regardless of `--stack agents`, so
  listing them as exclusive to this stack is misleading."*

This is a substantive correction relative to the current `skills.md`,
which lists every CLI as if it were stack-conditional.

## D. `SECURITY.md`

**Agree: do not stack-compose.**

> *"`SECURITY.md` carries vulnerability reporting, supported
> versions, secret-handling policy — repo-level concerns. Cloud
> runbooks are not the right thing to multiply at the root. Per-cloud
> secret guidance lives at `docs/secrets/<cloud>.md` (per the
> in-flight secrets-management proposal); root `SECURITY.md`
> just links to those."*

Single allowed exception: when `--stack secrets` is selected, add a
**short fixed reference line** to `SECURITY.md` pointing at
`docs/secrets/`. That's it. Don't compose AWS / Azure / GCP body
content into the root.

## E. Test strategy

```text
- python only → AGENTS.md mentions `uv run pytest`, has no `npm test`
- nextjs only → npm / Vercel guidance present; no `uv run pytest`
- python + azure → docs/agents/python.md and docs/agents/azure.md
  both generated
- .claude/skills/sunaba-python/SKILL.md has YAML frontmatter
- skills.md only contains tools for the selected stacks
- AGENTS.md is always ≤60 lines
- byte-identical for same stacks across two builds
- --stack nextjs --stack python keeps Next.js section above Python
- --no-devcontainer switches wording to host-only; no devcontainer-feature
  assumptions appear in body text
- legacy sync stays static-copy; opt-in sync runs the stack-aware builder
- stack-aware sync against an unregistered project errors out clearly
```

## F. Top-3 picks

1. **Introduce `_build_agent_files()` and the fragment layout.**
   Keeps `compose.py` clean; isolates the new responsibility.
2. **Make `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `skills.md`
   stack-aware.** Solves the immediate "irrelevant-stack advice"
   problem.
3. **`sync` opt-in mode + registry flag + structural tests.**
   Safety valve so existing users' files don't get rewritten by
   surprise.

> *"`.claude/skills/` and the `docs/agents/` mirror are
> high-value, but in the first PR they can land thinly or as a
> follow-up. Whatever we do, do **not** ship Claude skills first
> with no equivalent for Codex / Gemini — that violates cross-agent
> fairness."*

## G. Push-back

- **Putting Markdown bodies in `stacks/*.json`** (Gemini's main
  proposal). *"Breaks the spirit of the JSON-only deep-merge
  composer; PR-review is harder; escaping `\n` is annoying;
  syntax highlighting is lost."*
- **`@include` directives.** Not all agents share that semantic.
  Generated files should make sense as static text.
- **Skills-only as the canonical detail location.** sunaba is a
  three-agent sandbox. Claude-only progressive disclosure is a
  supplement, not the primary surface.
- **Composing `SECURITY.md`.** Security policy and cloud runbooks
  belong in different files. Composing increases the blast radius of
  any future `sync` mistake.

## What this leaves open for the synthesized proposal

Areas where Codex and Gemini gave materially different answers:

1. **Where Markdown content lives.** Codex says separate
   `templates/agents/fragments/<stack>/*.md` files; Gemini says
   string arrays inside `stacks/*.json`.
2. **How much detail goes into the root file.** Codex says root is
   an index (≤60 lines via short summaries that link to
   `docs/agents/<stack>.md`); Gemini says detail injected into root
   between delimiters.
3. **`sunaba sync` posture.** Codex wants registry mode flag +
   opt-in migration; Gemini wants delimiter-preserving replacement
   that works on existing files unconditionally.

These three decisions are what the synthesized proposal in
[`05-proposal.md`](05-proposal.md) has to take a position on.
